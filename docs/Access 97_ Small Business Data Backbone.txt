Systems Architecture and Data-Handling Paradigms of Microsoft Access 97 and the Jet 3.5 Engine
In the history of personal and enterprise computing, the 1990s represented a massive shift toward decentralized data systems.1 Prior to this era, database software was divided between terminal-based database systems and complex, command-line client-server architectures.1 The launch of Microsoft Access 97, powered by the Microsoft Jet 3.5 Database Engine, created a highly integrated, rapid application development environment.2 Together, Microsoft Access and Microsoft Excel became the primary data framework for small-to-medium-sized businesses.1 By analyzing the underlying binary storage models, network operating system file-locking services, memory caching protocols, and user interface binding mechanics, this report outlines the system architecture of this historic computing framework.
1. The Jet 3.5 Engine and Its Three-Tier ISAM Driver Architecture
The Microsoft Jet 3.5 Database Engine operates as a client-side, file-server-based database management system.7 Unlike centralized client-server Relational Database Management Systems (RDBMS) that run a continuous server-side daemon to manage disk Input/Output (I/O) and compile queries, the Jet engine loads entirely into the client workstation's local memory.7 The host server serves only as a passive storage volume, while the client computer handles all data processing and query execution.7

+------------------------------+------------------------------+

|   Native ISAM Driver         |   Installable ISAM Drivers   |
|     (MSJET35.DLL)            |     (MSJINT35/MSJTER35)      |

Jet 3.5 manages database operations using a three-tier Indexed Sequential Access Method (ISAM) driver model, which decouples logical operations from physical storage 9:
* The Native Jet ISAM Driver (MSJET35.DLL): This core dynamic link library (DLL) directly manipulates Microsoft Access database (.mdb) files.4 It communicates with the host operating system's random-access file system APIs, executing reads and writes on binary pages.9
* The Installable ISAM Drivers (MSJINT35.DLL, MSJTER35.DLL): These translation libraries allow Jet to connect natively to external data files.4 By translating external formats (such as FoxPro, Paradox, Btrieve, and dBase) into Jet's internal structures, these drivers enable users to run heterogeneous queries across different file formats.9
* The Data Access Objects (DAO 3.5) API: This interface exposes Jet's engine capabilities to developers using Visual Basic for Applications (VBA).4 DAO allows developers to manipulate schemas, indexes, and tables programmatically using an object model, hiding the complexities of binary page structures and lock protocols.4
2. Structural Analysis of the MDB Binary File Format
At the physical storage layer, the .mdb file format operates as a sequence of fixed-size binary blocks called pages.11 In Jet 3.5 (Access 97) databases, pages are exactly 2048 bytes (  ) in size, aligned on strict block boundaries.11 The first byte of each page identifies its type, which dictates how the remaining 2047 bytes are structured.11
A notable characteristic of the MDB file format is that Jet does not zero-out or initialize pages before writing them to disk.12 Consequently, newly allocated database pages often contain uninitialized memory residues (garbage data) from the host client's RAM.12 While this made early reverse-engineering efforts difficult, it also meant that sensitive temporary system data was frequently written directly into the binary layout of the .mdb file.12

Data Page Layout and Record Rows
Data Pages (Type 0x01) store actual row records.12 To optimize storage, Jet uses a reverse-growth model.12 The page header is written at the beginning of the page, moving downward, while the row records are written starting at the end of the page and move upward.12

| Page Header (Type 0x01, Free Space, Row Count)             |
+-----------------------------------------------------------+
| Row Offset Directory                                      |
|...                         |
|                                                           |
|                        (Free Space)                       |
|                                                           |
|                                                           |
|                             |
|                             |
+-----------------------------------------------------------+

The page header contains an array of two-byte integers that store the starting offsets of each row.12 These offsets use two high-order bits to signal structural flags:
* The Lookup Flag (0x40): When the high-order byte of a row offset contains 0x40, it indicates that the record exceeded the page capacity.12 This flag tells Jet to treat the offset as a pointer to a 4-byte overflow page address.12
* The Delete Flag (0x80): When the high-order byte of the row offset contains 0x80, the row is flagged as deleted.12 The engine skips this record during standard operations, and its space is reclaimed during the next compaction.12
Variable-Length Columns and Memo Storage
To parse a record row, the Jet engine must first access the corresponding Table Definition (TDEF) page (Type 0x02), which describes the column schemas.12 A row always begins with fixed-width columns (e.g., integers, doubles, booleans), which are stored in sequential, predictable byte ranges.12 Following the fixed-width data are the non-null variable-length columns (e.g., text, memo).12
Because variable columns can grow or shrink dynamically, Jet writes a variable-column offset table (known as the var_table) in reverse order at the end of the record.12 This table tracks the end position of each variable-width field relative to the start of the record.12

For unstructured text or large binary objects that exceed standard column limits, Jet utilizes 12-byte Memo fields in the row layout.12 Rather than storing large strings inline, Jet writes a 12-byte structural pointer containing:
1. Memo Length (3 Bytes): Stores the total size of the memo field.12
2. Bitmask Flag (1 Byte): Indicates the memo storage mode:
   * 0x80: The memo is stored as a string directly at the end of the row header (inline).12
   * 0x40: The memo is stored in a single, dedicated Long Value (LVAL) page.12
   * 0x00: The memo is split across multiple linked LVAL pages.12
3. Data Pointer (4 Bytes): The logical page address of the first LVAL page.12
4. Unknown Field (4 Bytes): Reserved space for internal engine tracking.12
3. Concurrency Control and the Lock File Engine (.ldb)
The absence of a centralized server-side database daemon required Jet to use an unconventional concurrency management system.7 Multi-user database systems depend on strict isolation and lock states to prevent data corruption when multiple users write to the database simultaneously.9 To solve this, Microsoft developed a coordinated locking scheme based on a separate file, the Lock Database (.ldb) file, which works in tandem with the network operating system's file-locking services.13
The Structural Layout of the Lock File
Whenever a client workstation opens an .mdb database file in shared mode, Jet automatically checks for the presence of a matching .ldb file in the same directory.13 If one does not exist, Jet creates it.15 The physical size of the .ldb file is strictly bounded.13 It is modeled as a one-dimensional array of 64-byte blocks, accommodating up to 255 concurrent users (the maximum supported limit of the engine).13 Consequently, the physical size of the lock file never exceeds 16,320 bytes:
  

Each 64-byte block contains two distinct metadata elements 13:
1. Computer Name (Bytes 1–32): The NetBIOS name of the workstation currently accessing the database.13
2. Workspace Security Name (Bytes 33–64): The active user account name supplied during authentication (often "Admin" by default).13
The Innovation of Extended Byte-Range Locking
To prevent the lock file from becoming a performance bottleneck, Jet does not continuously write lock state updates directly into the .ldb file.15 Instead, it uses extended byte-range locking, a mechanism that leverages the Windows file system's low-level locking APIs via SMB.8
Instead of locking physical bytes of the data file, Jet places lock requests on virtual address spaces that exist far beyond the physical End of File (EOF) of the .ldb file.15 These virtual locks are mapped to logical pages inside the .mdb file.15 Because these ranges do not correspond to physical disk sectors, Jet can lock thousands of virtual memory locations without causing physical file expansion or disk write overhead.15

+-----------------------------------------------------------------------+
| 0x20000000 - 0x2FF800FF  : Write Locks (Exclusive, 256-512 Bytes)      |
+-----------------------------------------------------------------------+
| 0x30000000 - 0x3FF800FF  : Read/Commit Locks (Shared, 1 Byte)          |
+-----------------------------------------------------------------------+

	Shared vs. Exclusive Locks
Jet handles data access using two primary lock types, which are applied to virtual addresses corresponding to physical page numbers in the .mdb file 15:
* Shared Locks (1 Byte): These locks allow multiple clients to read data concurrently without conflict.15 Shared locks are typically used when opening tables for reading or verifying index structures.15 Multiple shared locks can reside on the same virtual address without interfering with one another.15
* Exclusive Locks (256 to 512 Bytes): These locks are required for write operations.15 An exclusive lock is structured to lock the first 256 bytes of a virtual range.15 This blocks any new shared locks and reveals any existing shared locks.15 The remaining bytes of the lock range are used to store the user's identifier, allowing other clients to determine who holds the conflicting lock.15
The User-Lock Allocation Algorithm
When a client workstation connects to a database, the Jet engine coordinates identity mapping and integrity verification using a multi-step user-lock algorithm 15:






User Connection Attempt
 |
 +--> 1. Check DBH page for suspect state (non-zero commit byte)?
 |      |
 |      +--> Yes: Verify matching active lock in 10,000,000 hex range.
 |      |           |
 |      |           +--> Active Lock Missing? -> Halt and force Repair utility.
 |      |
 |      +--> No: Proceed.
 |
 +--> 2. Request 1-byte Shared Lock at 0x10000001.
 |      |
 |      +--> Blocked? -> Increment offset (0x10000002) and retry.
 |      |
 |      +--> Acquired? -> Lock successfully placed at offset [N].
 |
 +--> 3. Calculate physical write block offset: [N - 0x10000001] * 64 bytes.
 |
 +--> 4. Write NetBIOS name & Security credentials to physical slot in.ldb.

If the database is clean, Jet attempts to place a 1-byte shared lock at the beginning of the user-lock virtual address space (10000001 hex).15 If this address is already locked by another user, the engine increments the address by one byte (e.g., 10000002 hex) and retries.15
This process repeats until Jet successfully acquires an open lock byte.15 The offset of this acquired byte determines the user's physical slot in the .ldb file.15 For example, if Jet secures a lock at offset 10000003 hex (the third byte in the range), it writes the computer name and user credentials to the third 64-byte block in the physical .ldb file (starting at byte 128).15
4. Performance and Caching Optimizations in Jet 3.5
The release of Jet 3.5 in Office 97 introduced significant structural optimizations designed to minimize disk and network I/O, which was the primary bottleneck for desktop-bound file-server databases.4

	Jet 3.0 Engine Behavior
	Jet 3.5 Engine Optimization
	Business Operational Impact
	Referential Integrity Index Locks
	Write locks placed on index B-Trees during foreign key validation, blocking concurrent reads.4
	Replaced write locks with read locks on index pages that are not actively undergoing modification.4
	Resolves major concurrency bottlenecks in multi-user data entry forms.4
	Long Value (LV) Page Reads
	Read locks placed on every Memo/OLE page being read to guarantee transactional consistency.4
	Eliminated read locks on single-page LV objects (e.g., short text inside Memo fields).4
	Dramatically reduces lock collisions in text-heavy record exploration.4
	Registry and Config Control
	Fixed registry parameter values loaded globally at engine startup.4
	Programmatic run-time control over registry parameters via engine APIs.4
	Allows fine-tuning of memory, caching, and locking behavior dynamically in code.4
	Page Caching Mechanics
	Cache flushed every 2 seconds after each physical table extent (up to   ) is added.4
	Cache is only flushed 2 seconds after all cumulative new extent data is written.4
	Substantially minimizes disk write overhead during bulk record appending.4

	Page Recycling Mechanics and the RecycleLVs Option
In early iterations of Jet, modifying Long Value (LV) pages (such as altering forms, reports, or VBA modules) caused immediate database bloat.4 The physical space occupied by deleted or modified LVs could not be reclaimed without a manual "Compact and Repair" operation, or until the last active user disconnected from the database.4
Jet 3.5 resolved this by introducing dynamic page recycling, allowing the engine to reclaim and overwrite unused LV pages in real time.4 However, because this cleanup process introduced a minor performance penalty during write operations, Microsoft added a registry entry called RecycleLVs.4
This option is turned off by default to maintain raw writing speed.4 However, Microsoft Access dynamically toggles this setting on immediately before modifying design-level objects (which utilize LV storage) and disables it once the changes are written to disk, preventing development-time file bloat.4
The Core Paradigm Shift: Removal of Implicit Transactions
To guarantee database consistency, Jet 3.0 wrapped every individual SQL Data Manipulation Language (DML) statement (such as UPDATE, INSERT, or DELETE) in an implicit transaction.4 While this protected data integrity, it also introduced significant I/O overhead.4 Over high-latency local area networks, writing data inside these automatic transactions was incredibly slow.4 Often, custom VBA looping structures using Recordsets would outpace bulk SQL queries because the loops could bypass these transactional boundaries.4
Jet 3.5 resolved this bottleneck by removing implicit transactions from SQL DML operations.4 This change provided a massive performance boost for bulk data updates.4 However, it also shifted the responsibility of transaction management to the developer.4
Without an implicit transaction, if a bulk update affecting 10,000 rows is interrupted midway through execution (due to a crash or network dropout), Jet 3.5 does not roll back the completed modifications.4 Some records are saved, while others remain unchanged.4 To guarantee atomic updates, developers must explicitly wrap bulk operations in transaction blocks, accepting the associated performance trade-off 4:






VBA
On Error GoTo ErrorHandler
DBEngine.Workspaces(0).BeginTrans
CurrentDb.Execute "UPDATE tblInventory SET Price = Price * 1.05 WHERE Category = 'Electronics';", dbFailOnError
DBEngine.Workspaces(0).CommitTrans
Exit Sub

ErrorHandler:
   DBEngine.Workspaces(0).Rollback
   MsgBox "Update aborted due to error: " & Err.Description

5. MS Forms and the Data-Binding Engine
The success of Microsoft Access 97 as a Rapid Application Development (RAD) platform was largely due to its tight integration of the Microsoft Forms layout engine with the Jet database engine.5 This integration allowed developers to construct rich, data-bound user interfaces with minimal code.3
Dynasets vs. Snapshots
When an Access form is bound to a data source (a table, query, or SQL statement), the underlying Jet engine opens a specialized cursor called a Recordset.3 Jet handles this data retrieval using two primary Recordset models, each with distinct trade-offs 7:

	The Event-Driven Validation Pipeline
Access forms utilize an event-driven framework to coordinate data entry and validation.5 When a user modifies data in a bound control, the form acts as a gatekeeper.5 It manages the flow of changes using three primary engine events 18:

 |

 |      |
 |      +--> BeforeUpdate Event: Allows cancellation (Cancel = True) to roll back edits.
 |      |

 |

        |

* BeforeUpdate (Control and Form Levels): This event is critical for data integrity.18 It fires immediately before changed data is written to the recordset.18 Because it is cancellable (Cancel = True), developers can write validation rules to verify inputs before they are saved.3 If validation fails, the update is blocked, preventing invalid data from reaching the table.3
* AfterUpdate: This event fires immediately after the changes have been saved to disk.18 It is commonly used to update totals, recalculate derived fields, or trigger secondary processes.18
* OnCurrent: This event fires whenever focus shifts to a different row.19 It is used to synchronize child subforms, update calculated totals, or adjust the state of form controls based on the current record (such as locking historical records).19
Continuous Forms and Combo Box Design Challenges
Continuous Forms allow developers to display multiple records simultaneously in a tabular layout, with each row representing an instance of the form's detail section.16 However, this layout introduces a significant architectural limitation for bound combo boxes.19
Because the continuous rows are rendered as virtual instances of a single template, a combo box control shares its RowSource property across all visible rows.19 If a developer attempts to filter the combo box options dynamically based on the current row's data, changing the list options on one row immediately updates the dropdown list for all other rows.19 This causes display issues, often resulting in blank spaces or missing descriptions on adjacent records.19
To solve this, developers developed a clever overlay workaround 19:
1. A bound text box is placed on the form's detail section to display the read-only, descriptive value of the field.19
2. An unbound combo box is positioned exactly over the text box.19
3. In the text box's OnEnter or OnClick event, focus is programmatically shifted to the combo box, bringing it to the foreground for data entry.19
4. When the user selects an option, the combo box's AfterUpdate event writes the selected value back to the underlying text box.19
5. When focus leaves the combo box, it is returned to the background, and the text box displays the updated value.19
6. Access-Excel Interoperability and Small Business Workflows
During the 1990s, the integration of Microsoft Access and Excel became the technical backbone for business data management.1 This combination bridged the gap between basic spreadsheets and complex enterprise database systems.6 Access functioned as the structured, relational data store—enforcing relationships, referential integrity, and multi-user access—while Excel served as the analytical playground for modeling, graphing, and financial forecasting.2
Data Integration Pipelines
To coordinate this workflow, developers relied on several automated data transfer mechanisms 22:
* DoCmd.TransferSpreadsheet: A native VBA command that allowed developers to import or export entire tables and queries directly between Access and Excel files.23 This command used specific parameters, such as acSpreadsheetTypeExcel8 (represented by the parameter value 8), which explicitly formatted files to be compatible with Excel 97 through Excel 2000.25
* DoCmd.TransferText: Used to move delimited structures, such as CSV files, between applications.23 If standard localization conflicts arose (e.g., mismatching regional decimal points), developers defined customized export patterns.26 These settings were written directly to the database system tables inside the MSysIMEXSpecs table, ensuring consistent data mapping.26
* Microsoft Query (MS Query): An Excel add-in that allowed analysts to query local Access databases directly from a spreadsheet.27 Using Open Database Connectivity (ODBC), MS Query allowed users to write custom SQL statements against an Access database and load the results directly into an Excel sheet, establishing a live data link.22
* VBA Automation and Library References: Through Component Object Model (COM) automation, developers could reference Excel's object model directly from Access (and vice versa).28 This allowed Access databases to launch Excel, open workbooks, write values to specific cells, format spreadsheets, and generate charts programmatically, creating seamless, end-to-end reporting pipelines.29

	Causal Mapping of Network Dropouts to Binary Corruption
Because Jet runs entirely on the client, when a database modification is requested, the client must pull the relevant index and data pages into local RAM, make the edits, and write the modified pages back to disk over the network.6






Client Modifying Record
 |
 +--> 1. Client locks virtual byte range in.ldb.
 |
 +--> 2. Client reads physical page from.mdb over SMB into local RAM.
 |
 +--> 3. Local Jet engine modifies data bytes in RAM.
 |
 +--> 4. Client attempts to write modified page back to disk.
 |
 |      ** NETWORK DROP/WIFI HIC_CUP OCCURS **
 |
 +--> 5. Write operation is abruptly terminated.
 |
 +--> 6. Page contains unaligned header offsets and half-written data.
 |
 +--> 7. Result: Database immediately becomes corrupted.

If the network connection drops (due to a bad cable, switch reset, or Wi-Fi dropout) while the client is writing a page back to disk, the write operation is cut short.6 Since Jet 3.5 does not have server-side transaction logging, this incomplete write leaves the binary page structure in an unaligned, half-written state.6 The next time the engine attempts to parse that page, the byte offsets fail validation, resulting in immediate database corruption.6
Compilation States and VBA Code Corruption
Access databases are highly vulnerable to compile-state corruption during development.33 Internally, Access tracks three separate representations of VBA code modules simultaneously: the raw source text, the temporary text generated during editing, and the compiled p-code.33
If a developer edits a code module in break mode (while the engine is paused on an active execution thread), the compilation manager can lose track of these pointers.33 This results in a mismatched compile state, rendering the code uncompilable.33
To resolve this issue, developers rely on the command-line /decompile switch.33 Launching Access with this flag forces the engine to strip away the compiled p-code entirely, leaving only the raw source text.33 This allows the developer to re-compile the modules from scratch, repairing the code structure.33
The Distribution of Compiled Databases (.mde)
To prevent end-users from modifying design-level objects or introducing compilation errors in production, developers compile databases into the .mde format (or .accde in newer versions).33
Converting an .mdb database to an .mde file strips away the raw VBA source code entirely, leaving only the compiled p-code executable bytes.33 This process secures intellectual property and prevents compile-state corruption.33 However, because the source code is completely discarded, developers must retain the original .mdb file, as an .mde database cannot be decompiled back into its editable source format.37
Workgroup Security (.mdw) and Decoupled Security System Vulnerabilities
Jet 3.5 attempted to implement user-level security using separate Workgroup Information Files (.mdw), typically named system.mdw.34 This file stored user credentials, group memberships, and personal identification codes (PIDs).38
However, this architecture had a critical security flaw: it was entirely decoupled from the database itself.34 The .mdb file only stored security permissions mapped to group and user IDs, while the .mdw file verified the user's identity.34
This decoupled design introduced a significant vulnerability 34:
1. If an attacker copied the .mdb database file without the accompanying .mdw file, they could bypass the security constraints entirely.34
2. By linking the database to a newly created, default .mdw file where they held administrative credentials, the attacker could gain full access to the database tables.36
3. Additionally, because both the database password and user credentials were stored using weak, early encryption algorithms, attackers could easily extract credentials using simple binary decryption tools.35
Conclusions
The success of Microsoft Access 97 and the Jet 3.5 Database Engine was due to their cohesive, all-in-one design.2 By packing a relational database, a multi-user locking system, a dynamic form layout engine, and a programming language (VBA) into a single desktop application, Microsoft dramatically lowered the barrier to entry for software development.2
Despite its vulnerabilities to network instability, physical file limits, and weak security models, the Access-Excel ecosystem served as a powerful, rapid prototyping platform.2 It empowered business users to build custom, data-driven solutions independently, establishing a legacy of agile, decentralized computing that continues to influence modern application design.2
