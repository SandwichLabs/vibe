# Storage setup from the lake form, and AWS SSO sign-in for S3

Status: **plan** (2026-10-15). Issues #130 (detect storage URLs and set up the storage connection inline) and #131 (AWS SSO / profile sign-in for S3, with a `.env`-style sign-in prompt). Builds on #118 (`docs/plans/ducklake-catalogs.md`): `checkStorageURLs`, `Spec.Requires`, `connectRequires` / `detachDependents` / `readyDependents` (#124), `use_ssl` (#119). Related: #127 (the rail's "Fix" on a dependency error), #116 (the agent's URL-read boundary).

## Goal

1. **#130.** A person typing an object-storage URL into a DuckLake, Iceberg or Delta form sees at once whether a storage connection covers it. If none does, one click opens a prefilled storage form (type, scope, name, own scope), with presets for S3-compatible stores, and saving it returns to the lake with the dependency resolved. Test on the lake tests the storage connection first and says which one failed. The CLI says which `vibe conn add` command is missing.
2. **#131.** An S3 connection can sign in with a person's **AWS IAM Identity Center (SSO) profile** from `~/.aws/config`. Only the profile name is stored (per person, never committed). Keys are resolved at connect time, live only in process memory and the DuckDB temporary secret, keep the connection's `SCOPE`, are rotated before they expire, and an expired session shows a "Sign in" prompt that runs the device-authorization flow natively. Headless `vibe mcp serve` reports "needs sign-in" and never waits on a browser.

## Non-goals

- Ambient AWS credentials: the default chain, environment `AWS_*`, instance metadata, `credential_process`, `source_profile` / `role_arn` chains, static-key profiles. v1 is SSO profiles only (see [Later](#later)).
- GCS `gcloud auth application-default login` and Azure `az login`. The sign-in abstraction is kept general (a method *kind* with a provider), but only `aws-sso` ships.
- Creating buckets, or writing anything to object storage.
- Changing the storage-scope rule itself: `storageurl.Within` stays the one rule for the workspace and the agent.
- The rail "Fix" action of #127 (separate issue; this plan makes the error rarer and gives #127 a target to open).

## What is there today (grounding)

- **The match rule.** `checkStorageURLs` / `checkStorageURL` (`internal/workspace/connect.go:177-229`) run only in `ResolveConnection` (open/resolve), not at save. They match the catalog URL, `data_path` (ducklake) or `path` (iceberg, delta) against every storage connection of the workspace (`ws.Connections()`, all scopes merged) with `storageurl.Within`; the longest scope wins, ties go to the first by name; the result is `ResolvedConnection.Requires`. With no match the error is "the catalog … is not inside the scope of any S3, GCS, R2 or Azure connection of this workspace; add one whose scope contains it".
- **Schemes are literal.** `storageurl` never aliases schemes: a `gs://` URL does not match a `gcs://` scope (`internal/storageurl/storageurl.go:1-12`). A suggested scope must reuse the URL's own scheme.
- **Storage types.** `storageType` (`internal/connections/storage.go`) for s3/gcs/r2: scope required and must name a bucket; s3 options `endpoint`, `url_style`, `use_ssl`; r2 needs `account_id`. `SecretSteps` builds `KEY_ID`, `SECRET`, optional `SESSION_TOKEN` (s3), `REGION`, `ENDPOINT`, `URL_STYLE`, `USE_SSL`, always `SCOPE`. `SignInMethods: keychain, env, prompt`. `azureType` (`azure.go`) is the precedent for a sign-in choice, as a *definition* option (`sign_in`), and documents why `credential_chain` is refused.
- **Sign-in methods are per person.** `secrets.ParseMethod` (`internal/secrets/resolver.go:127`) knows `keychain`, `prompt`, `env:PREFIX`; `workspace.ValidateSignIn` (`internal/workspace/config.go:127`) checks the same. The method lives in `local.yaml` / user `connections.yaml` with `sign_in_fingerprint`; a committed `credentials:` is only a hint (`docs/reference/workspaces.md:177`). `signInGuard` (`connect.go:87-100`) withholds an `env:` credential whose fingerprint no longer matches; `TestCredential` (`internal/workspace/testcred.go:34`) applies the same; `setSignIn` (`conn_crud.go:404-434`) asks for confirm-rebind only for `env`. `TypeInfo.SignInMethods` is advertised to the form but not enforced on save; lakes and tables declare an empty list (they need no credential) and `ListConnectionTypes` (`studio/connections_crud.go:77-80`) shows the default three for an empty list.
- **The resolver is built in three places**, not one: `cliResolver` (`cmd/wsopen.go:50-52`, also used by `vibe mcp serve` through `hub.Open`), `studio/app.go:194`, and the default in `workspace.Open` (`internal/workspace/workspace.go:223-225`). Each passes `secrets.WithEnv(workspace.SnapshotEnv())`.
- **Preflight is synchronous at open**: `registerAll` (`internal/workspace/session.go:229-260`) calls `sess.Preflight` for every non-eager connection in turn, so a slow credential lookup delays the workspace open.
- **Credentials reach DuckDB** through `Spec.Credential` (`internal/workspace/session.go:197-210`) → `hub.readyForConnect` → `ct.SecretSteps` → `createSecretOn` (never logged), and `h.redactor.AddCredential(cred)` (`internal/session/session_connect.go:248-292`).
- **Storage lifecycle.** `Preflight` (`session_connect.go:312-368`) creates a storage secret at open; on a credential change it first `detachDependents`, then drops and re-creates (fail closed: if a dependent cannot be detached the old secret stays). `readyDependents` resets "needs the X connection" dependents and re-preflights catalogless ones (`internal/session/requires.go`). There is **no status listener**: Studio learns about status changes only from its own calls (`emitStatus`, `studio/connections_sync.go:165-188`).
- **Test.** `TestConnection` (`studio/connections_probe.go:50-102`) and `vibe conn test` (`cmd/conn.go:329-361`) each call `ResolveConnection` + `TestCredential` + `connections.Test` on one definition in a throwaway session without any storage secret, so a URL lake or table short-circuits (`tablesource.go:87-89`, `attachesOnlyInWorkspace` in `test.go:270-276`, and the ducklake equivalent from #118 step 4).
- **The editor.** `ConnectionEditorView.vue` (248 lines, ~30 script lines) wires `useConnectionForm` (300 lines; loads blank, `?from=` duplicate, or a saved connection), `useConnectionEditor` (test/save/remove; leave-with-unsaved-edits guard via `onBeforeRouteLeave`), `useMotherDuckPicker`. The form is generated from `TypeInfo.Fields`. **`?scope=` is taken**: on the edit route it is the connection's workspace scope (`useConnectionForm.ts:256`), and `useConnectionEditor` reloads when it changes (`:214`). Markdown links render only `http(s)` hrefs (`lib/markdown.ts:127-128`), so a notebook cannot link into `#/connections/new?...`.
- **The `.env` prompt.** `useDotEnv.ts` is a module singleton (state ref, `notNowFor` per workspace open, cleared on `workspace:opened`), rendered by `WorkspaceBanner.vue` (111 lines, which starts the tracking in its own `onMounted`), and the Go side re-registers affected connections (`refreshEnvConnections`, `studio/dotenv.go:62-103`) then the frontend calls `refreshConnections()`.
- **CLI.** `vibe conn add` (`cmd/conn.go:104-192`) saves without a storage check (by design: a lake may be saved before its storage connection) and prints only "Added …".
- **Agent.** The agent reads only `data/` files and URLs inside a ready storage scope (`internal/agents/sql_paths.go`); `duckdb_secrets`, `which_secret`, `getenv` are denied (`sql_names.go:164-166`, `sql_plan.go:24`). Nothing in either issue may widen this.
- **Dependencies.** `aws-sdk-go-v2` `config`, `credentials` (with `ssocreds`), `service/sso` and `service/ssooidc` are **already in the module graph**, indirectly, via `charm.land/fantasy/providers/anthropic` (Bedrock) (`go mod why -m github.com/aws/aws-sdk-go-v2/config`; `THIRD_PARTY_NOTICES.md` already lists them). The Go-side approach promotes them to direct requirements; it adds no module. (Checked 2026-10-15: `config v1.33.1`, `credentials v1.20.1`, `service/sso v1.35.1`, `service/ssooidc v1.40.1`, all `// indirect` in `go.mod`.) In that SDK, `ssocreds.SSOTokenProvider` refreshes only when the cached token file holds `refreshToken`, `clientId` **and** `clientSecret`, and writes the refreshed token back to the same file itself (temp name + rename, `O_CREATE|O_TRUNC`, no `O_EXCL`, no `MkdirAll`).

## Spike: DuckDB's `aws` extension (run 2026-10-15)

Run with the DuckDB **CLI 1.5.5** (the Go hub is on 1.5.6; the CLI is the only DuckDB with a shell here), `aws` extension `efa54a9` installed from `core` into a scratch extension directory, `HOME` pointed at a scratch `~/.aws` holding a fake `sso-session` profile, a legacy-format SSO profile and a static-key profile. There is no real Identity Center here and no AWS CLI.

**Verified:**

- `CREATE SECRET (TYPE s3, PROVIDER credential_chain, CHAIN 'sso', PROFILE 'p', SCOPE 's3://b/')` **fails at CREATE** when the SSO session is missing, expired, or present but refused (a fake cached token): always the same text, `Invalid Configuration Error: Secret Validation Failure: during 'generate' using the following: Profile: 'p' Credential Chain: 'sso'`. DuckDB cannot tell "you need to sign in" from "the portal refused you" or "offline".
- `CHAIN 'sso'` does **not** fall back to `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` in the environment, nor to `AWS_PROFILE` pointing at a static profile: both still fail. An unknown chain name (`'bogus'`) is refused at bind time.
- `PROFILE 'nope'` fails with a message that **includes the local path of the config file** (it would reach the UI and the agent's error text unless redacted).
- `REFRESH 'auto'` is accepted and stored in the secret's `refresh_info` (`{'validation': none, 'refresh': auto, 'profile': p, 'chain': sso}`); `REFRESH 'bogus'` is accepted too (no value check).
- `VALIDATION 'none'` makes `CREATE SECRET` **succeed with no credentials at all** (the secret then reads anonymously). It must never be used.
- `CHAIN 'config', PROFILE 'static'` works and `duckdb_secrets()` shows the `key_id` (the secret and a `session_token=redacted` field, even when the profile has no token). Unredacted display is refused.
- Unknown parameters are refused (`Binder Error: Unknown parameter 'foo' for secret type 's3' with provider 'credential_chain'`).

**Not verified (no Identity Center, no network test):** what `REFRESH 'auto'` actually does on an expired token at read time (re-run the chain on a 403? once? under which lock?); whether the C++ SDK reads `sso-session` sections and refreshes with a refresh token; the S3 error text for an expired session token through httpfs (`ExpiredToken` / `The provided token has expired` is assumed); behaviour on 1.5.6 in the Go hub (same extension line, assumed identical).

### Spike: in-place secret rotation on the Go hub (run 2026-10-16, step 5)

Run on the Go hub (DuckDB 1.5.6) against MinIO (`docker.io/minio/minio`) with a throwaway integration test (not committed). Credentials came from MinIO STS `AssumeRole` (the `aws-sdk-go-v2` `service/sts` client, root keys as the caller), written as the same `SCOPE` / `KEY_ID` / `SECRET` / `SESSION_TOKEN` / `REGION` / `ENDPOINT` / `URL_STYLE` / `USE_SSL` secret `storageType.SecretSteps` writes, through `session.CreateTemporarySecret` (`CREATE OR REPLACE TEMPORARY SECRET`, same name, no drop, no detach). A URL-catalog DuckLake (`store` secret scope `s3://lake/`) was attached.

**Verified:**

- **In-place rotation with *different* STS credentials while a lake reads.** Four goroutines read `read_parquet('s3://lake/spike/a.parquet')` and the lake (`SELECT count(*) FROM lake.people`) in a loop while the secret was replaced 20 times, alternating two distinct STS sets (different key id, secret and session token): 851 reads, **0 failures**. A fresh object (never read before, so not in DuckDB's external file cache) read after a rotation succeeds and `which_secret('s3://lake/spike/fresh.parquet', 's3')` names `store`. Nothing read anonymously.
- **A bad replacement fails closed and the old data does not mask it.** Replacing the secret with the right key and secret but a wrong session token, an empty session token for an STS key, or a wrong secret makes both a fresh object and the lake's own parquet file fail with HTTP 403 (so the external file cache did not hide the failure). Exact texts, for the classifier of step 7 (DuckDB wraps them as `HTTP Error: HTTP GET error reading '<url>' in region '<r>' (HTTP 403 Forbidden)` + the S3 body + `Authentication Failure - this is usually caused by invalid or missing credentials.`):
  - wrong or empty session token: `InvalidTokenId: The security token included in the request is invalid`
  - wrong secret: `SignatureDoesNotMatch: The request signature we calculated does not match the signature you provided. Check your key and signing method.`
- MinIO STS accepts a `DurationSeconds` of 900 or more only (`InvalidParameterValue: invalid token expiry` for 1 and 60).

**Assumed (not verified):** the text of a genuinely **expired** session token. MinIO cannot mint one in test time (15 minute minimum), so the real S3 `ExpiredToken` / `The provided token has expired` text is still an assumption. The step 7 classifier should match on the HTTP 403 plus any of `ExpiredToken`, `InvalidTokenId`, `The security token included in the request is expired|invalid` and treat all as `needs-credentials`, which is also right for a revoked set. Real IAM Identity Center behaviour (portal error for a revoked token, `sso-session` refresh end to end, the device page's host) is open question 1 and was not run.

**Notes for steps 6-7 from #135, #138 and #141 (nothing implemented in step 5):**

- Every secret that carries SSO credentials must write explicit `SESSION_TOKEN` and `REGION` (the spike's secret does; `storageType.SecretSteps` already does), never rely on the host's `AWS_*` (#135), keep `s3_url_compatibility_mode` on and load httpfs only through `session.EnsureExtension` / `DenyUncoveredStorage` (#138). The per-secret `URL_COMPATIBILITY_MODE` stays unused.
- **The wildcard lister (#141) builds a connection's secret itself.** `hub.ListMatching` and `ListObjects` call `h.secretFor(ctx, spec)` on every listing, which calls `spec.Credential`. With `aws-sso:PROFILE` that call is `awssso.Provider.Credentials`, so it must (1) come from the in-memory cache (it does until `Expires` minus 5 minutes; a listing must not cost a portal round trip each time), (2) fail with the `needs-credentials` sign-in hint rather than build an empty or anonymous secret when the session is gone, and (3) not depend on a rotation having run: the lister reads `secretFor`, not `ConnectReferenced`, so the secret it builds is always the freshest resolved set. Step 6's tests should cover `vibe query` / agent wildcard reads and `Test` (which uses the same private listing session) with a fake SSO profile.

## Decisions

### D1. #130: one match rule, exposed read-only

`workspace.StorageFor(ws, urls, lookup)` wraps the existing `checkStorageURL` loop (no second implementation) and returns, per URL, the matched connection (name, type, scope, which of user/shared/local it comes from) or a suggestion. The Studio binding sends URLs only and gets back names, scopes and statuses, all of which `ListConnections` already shows. The save path is unchanged (a lake may still be saved before its storage connection).

### D2. #130: the suggestion is computed in Go, not in the form

`internal/storageurl` gains `Bucket(u)` (scheme + bucket/container, `s3://b/`; for `abfss://c@acct.dfs.core.windows.net/…` the container and host) and `CommonFolder(urls)` (longest common prefix at a `/` boundary, never shorter than the bucket, never the bare scheme). `internal/connections` gains `StorageTypeForScheme(scheme)` (`s3://`, `s3a://`, `s3n://` → s3; `gs://`, `gcs://` → gcs; `r2://` → r2; `az://`, `azure://`, `abfss://` → azure). A suggestion is `{type, scope, name}` where scope is the **common folder** of the URLs in one bucket (catalog's folder, not the file), with the bucket offered as an explicit wider choice; URLs in two buckets or two schemes give two suggestions. The scheme is kept as typed (a `gs://` URL suggests a `gs://` scope). The name follows `connname` (lowercase, `[a-z0-9_]`, leading digit prefixed with the type, de-duplicated with `_2`, reserved names avoided). The CLI hint and the Studio form use the same function, so they cannot disagree.

### D3. #130: the nested form is the same editor, by route

"Set up storage" stashes the lake draft (no credentials exist on a lake form: nothing secret is stashed) in an in-memory module singleton (`useConnectionDraft`), then routes to `/connections/new?type=s3&prefix=…&name=…&in=local&return=lake-draft` (`prefix`, as the CLI's `--prefix`, because `?scope=` already means the workspace scope on this view). The storage connection is therefore entered through the **same** editor, sign-in section and `SetConnectionCredentials` bridge as any other (the issue's constraint), and its scope picker defaults to the lake's own scope (`local` or `user`). Saving with `return=lake-draft` routes back to `/connections/new?resume=1` and restores the draft; detection then shows "Read with **name**". Cancel returns to the draft too. The leave guard is skipped for this hand-off only (the draft is not lost). A modal embedding a second `useConnectionForm` was rejected: the form composables read `useRoute()` (new vs edit, `?from=`), and a second copy of the sign-in UI would be a second credential path to review.

### D4. #130: presets are registry data

`TypeInfo` gains `Presets []Preset` (`{id, label, options: {endpoint, url_style, use_ssl}, regionHint, help}`) for s3 only: **AWS** (no options), **MinIO** (`localhost:9000`, `path`, `use_ssl=false`), **Backblaze B2** (`s3.<region>.backblazeb2.com`, `vhost`, TLS on), **Floci** (`localhost:4566`, `path`, `use_ssl=false`), **Other S3-compatible** (empty endpoint, shows the fields). A `<region>` placeholder in an endpoint is filled from the Region field and must be replaced before save (validation stays `endptRE`). Presets only fill fields; nothing new reaches the definition (no `preset:` key is stored, so nothing new is fingerprinted). The CLI gets `vibe conn add --preset b2` (mirror), `internal/docsref` checks every preset id appears in `connections.md`. The Floci port is an assumption (its default; #118 used 4567): confirm before shipping.

### D5. #130: Test runs the requirement first, in the same throwaway session

`connections.Test` gains `WithRequiredStorage(def Def, cred secrets.Credential)` (repeatable). The throwaway session creates the storage secret(s) first; a failure there is reported as the storage connection's failure ("storage connection `floci`: needs credentials"), and the lake is not attempted. When they succeed, the lake/table is tested **for real** against them (the URL short-circuit in `tableSourceType.Probe` / `ducklakeType.Probe` / `runTest` is lifted only when a covering storage secret is present), which also runs the #118 catalog vetting over httpfs. `workspace.TestWithRequirements(ctx, ws, rc, signIn, typed)` resolves `rc.Requires` to saved definitions and their saved credentials (`TestCredential` with the storage connection's own sign-in, fingerprint guard included) and calls `connections.Test`; Studio's `probe` and `vibe conn test` both call it (today they duplicate the resolve/credential/test sequence). `TestResultView` gains `Requirement string` (the storage connection that failed, "" when the lake itself failed).

### D6. #131: resolve on the Go side, not with DuckDB's `credential_chain`

Resolve SSO credentials in Go with `aws-sdk-go-v2` (`config.LoadSharedConfigProfile` for the profile only, `ssocreds.SSOTokenProvider` + `ssocreds.New` for the role credentials) and hand DuckDB the same static `KEY_ID` / `SECRET` / `SESSION_TOKEN` + `SCOPE` secret it already gets. Against the trust rules:

| Requirement | Go-side (chosen) | DuckDB `credential_chain` (rejected) |
|---|---|---|
| Keys never in logs, errors, agent output | The keys pass through `Resolver` → `Redactor.AddCredential` like every other credential, so any DuckDB or S3 error that echoes them is scrubbed. | Keys exist only inside DuckDB; our redactor never learns them. `duckdb_secrets()` shows the key id (the agent's deny list covers it, but nothing else does). A missing profile's error carries a local file path. |
| Scope preserved | Unchanged `storageType.SecretSteps`: `SCOPE` always set, same code path as today. | Possible (`SCOPE` is accepted), but a second secret builder to keep in step. |
| Explicit chain, fail closed | Our code builds exactly one provider (SSO for the named profile); it never calls `config.LoadDefaultConfig`, so no env, IMDS, `credential_process` or default profile. A non-SSO profile is refused. | `CHAIN 'sso'` held in the spike, but the chain logic is the C++ SDK's; `VALIDATION 'none'` would create an empty secret that reads anonymously. |
| Session state ("signed in / expired") | Read from the SSO token cache without network; the portal's refusal is distinguishable from "no token" and "offline". | One opaque "Secret Validation Failure" for all three (verified). |
| Expiry | We know `Expires`; rotate in place before it (D9). | `REFRESH 'auto'` exists but its runtime behaviour is unverified and happens inside DuckDB, out of our locking and status. |
| Headless MCP | Resolution reads the cache and calls the portal with a timeout; it never opens a browser. | Same, but with no way to say *why* it failed. |
| Extension consent | No new extension. | `aws` becomes a new extension for s3 (consent flow, `InstallExtension` allow-list, `SpecExtensions` by sign-in method), and loads `load_aws_credentials()` into the hub. |

Cost: Vibe holds short-lived keys in process memory for the life of the secret (it already holds keychain secrets the same way), and the SDK modules become direct dependencies (already compiled in).

### D7. #131: `aws-sso:PROFILE` is a per-person sign-in method, not a definition option

Azure's `sign_in` is a committed option; the AWS profile is not. Profile names are local to a person's `~/.aws/config`, two teammates may sign in to the same bucket differently (keys vs SSO), and a committed definition must never choose how a person's identity is used (review #115). So the new method sits beside `keychain`, `prompt` and `env:PREFIX`:

- `secrets.ParseMethod` returns kind `aws-sso` with the profile; `workspace.ValidateSignIn` accepts `aws-sso:` + `^[A-Za-z0-9][A-Za-z0-9_.+@-]{0,63}$` (a safe subset of AWS profile names; refuse anything else with a clear message).
- It is offered only where `TypeInfo.SignInMethods` lists it: `s3` gets `aws-sso`; `SetSignIn` now **enforces** `SignInMethods` (today a UI hint only). An empty list means the type takes no credential, so `SetSignIn` refuses every method for it (Studio sends no sign-in for those: `needsSignIn` is false); the display fallback in `ListConnectionTypes` stays as it is.
- The name is decided: `aws-sso:PROFILE`. The method is one string in `sign_in` (as `env:PREFIX`), so it needs no second per-person key; `aws-sso` (not `aws-profile`) because only SSO profiles are accepted, which leaves `aws-profile:` free for [Later](#later).
- It is **bound to the definition fingerprint** like `env:` (`signInGuard`, `TestCredential`, the confirm-rebind on save): a pulled commit that changes the scope, region or endpoint withholds the SSO credentials until the person re-confirms.
- It is refused when the connection has `use_ssl=false`, or an `endpoint` that is not empty and does not match the S3-shaped `^(?:[a-z0-9-]+\.)*s3(?:-fips)?(?:[.-]dualstack)?(?:[.-][a-z0-9-]+)?(?:\.vpce)?\.amazonaws\.com(?:\.cn)?$` (lower case, no port, no colon: `endptRE` allows `:`, and `evil.example:443.amazonaws.com` must not pass a suffix check). AWS identity credentials go only to AWS S3 over TLS. This covers regional, dash-region, FIPS, dual-stack and S3 VPC-interface endpoints. **Changed in step 6 review:** "any host under `amazonaws.com`" admitted API Gateway (`execute-api`), AppSync, EC2, ELB, RDS and `s3-object-lambda` hosts, which run customer code behind AWS's own valid certificates and would receive the signed request (key id, session token, signature). An endpoint written as `${VAR}` is refused with its own message. A test-only hook (`export_test.go` in `workspace`, plus the `internal/hub` test option of step 6) lifts this for the MinIO integration tests.
- `SetCredentials` / `ClearCredentialField` refuse it like `env:` (`ErrReadOnly`: "an AWS SSO sign-in has no stored secret; sign in with your profile").
- CLI: `--sign-in aws-sso:PROFILE` on `conn add` and `conn credentials set` (the issue's `--sign-in profile --profile <name>` is the same information in one flag, matching `env:PREFIX`).

### D8. #131: the device flow is native (ssooidc), and shares the AWS CLI's token cache

Native `ssooidc` (`RegisterClient` → `StartDeviceAuthorization` → poll `CreateToken`, honouring `interval`, `slow_down`, `authorization_pending` and `expiresIn`) rather than shelling out to `aws sso login`:

- no dependency on the AWS CLI being installed and on `PATH` (it is not, on this machine), and no PATH-hijack or output-parsing surface;
- the user code is shown in Vibe next to the browser, so the person can check it matches;
- cancellable with a context, bounded, and never started headless.

**Decided: Vibe reads and writes the shared SSO token cache** (`ssocreds.StandardCachedTokenFilepath`, `~/.aws/sso/cache/<sha1 of the sso-session name or start URL>.json`), rather than keeping the token in memory only:

- Reading it is what makes the hint "or run `aws sso login --profile p`" work, and it is where a person who already uses the AWS CLI is signed in.
- `SSOTokenProvider` writes refreshed tokens back to whatever path it is given, so "memory only" would mean not using the SDK's refresh at all.
- It weakens no trust rule: the file is in the person's home, outside the workspace, not a config file, bundle, log or UI error, and outside the agent's read boundary (files only inside `data/`, symlinks resolved; step 9 asserts `read_text` on it is refused from every tier).

What Vibe writes matches the AWS CLI, so that each sees the other's session and the SDK can refresh it: `startUrl`, `region`, `accessToken`, `expiresAt`, and for an `sso-session` profile also `refreshToken`, `clientId`, `clientSecret`, `registrationExpiresAt` (the SDK refreshes only with all three of `refreshToken`/`clientId`/`clientSecret`). For an `sso-session` profile, `RegisterClient` asks for `grantTypes` `device_code` + `refresh_token`, `scopes` `sso:account:access` (or the profile's `sso_registration_scopes`) and `issuerUrl` = the start URL; a legacy profile gets no refresh token, and its registration is kept in memory for the flow only. Vibe's own write `MkdirAll`s `~/.aws/sso/cache` with 0700, writes a temp file in that directory with `O_CREATE|O_EXCL` and 0600, then renames it; the SDK's refresh write is the SDK's (it is the same file the AWS CLI rewrites). Role credentials (key, secret, session token) are **never** written to disk (the CLI's `~/.aws/cli/cache` is not used).

The verification URL is opened only if it parses as `https://`, with a lower-case ASCII host (no `xn--` label, no user info, no port) that is one of the pages Identity Center serves the device page from, **derived from the profile** (review of step 5): `device.sso.<sso_region>.amazonaws.com` (`.amazonaws.com.cn` for `cn-*` regions), `*.awsapps.com`, `*.awsapps.cn`, or `*.portal.<sso_region>.app.aws`; or the test endpoint (loopback only; a non-loopback `WithTestEndpoints` makes `Credentials` and `DeviceLogin` fail before any network call). `LoadProfile` also requires the profile's `sso_start_url` host to be `*.awsapps.com`, `*.awsapps.cn` or `*.portal.<sso_region>.app.aws`, so a custom start-URL host is refused (the start URL is where the person signs in). The generic `amazonaws.com`, `amazonaws.com.cn` and `aws` suffixes are **not** accepted: anyone can host a page under `s3.amazonaws.com`, `execute-api` or `*.on.aws`. (Hosts are from public docs, not yet checked against a real Identity Center: open question 1.) Studio opens it with Wails `runtime.BrowserOpenURL`. The CLI **prints** the URL and the code and opens nothing (no `exec` of `xdg-open`/`open`/`rundll32` in `cmd/`, so no argument-injection surface; an opener is [Later](#later)).

### D9. #131: expiry is handled by rotating the secret in place

The SSO `Credential` carries a non-secret `Expires` (`json:"-"`: never stored). The hub, after it creates a storage secret from a credential with `Expires`, keeps the deadline and:

1. **Before every statement** (in `ConnectReferenced`, which `internal/engine/engine.go:116` and `internal/agents/handler.go:241` call before running SQL; step 7 checks that the CRUD, table-paging and notebook paths reach it too, or adds the check where they don't), compares the **wall clock** with each SSO secret's deadline minus 5 minutes; a timer alone is not enough because Go's monotonic timers stop during laptop suspend.
2. No background timer (cut in review; see [Later](#later)): the issue asks for the prompt "when an SSO connection is used", and the check before every statement already covers a laptop that slept. An idle Studio may show a connection as ok whose keys have lapsed; its next statement rotates or fails closed.
3. **Rotate** (new `hub.rotate(name)`, one at a time per connection, with concurrent callers waiting on the same rotation): re-resolve the credential **without holding `adminMu`** (it is a network call of up to 5 s, and `adminMu` serialises every ATTACH/DETACH), bypassing the in-memory role-credential cache in `awssso`; then take `adminMu`, check the entry is still the one that was resolved (not unregistered, re-registered with a new spec or re-preflighted meanwhile; otherwise discard the result), and on success `CREATE OR REPLACE TEMPORARY SECRET` with the **same name**, no drop and no detach, so the secret is never absent and dependents never read anonymously (the #118 spike showed replace-in-place keeps an attached lake reading; step 5 re-checks it with *different* credentials). On failure (session expired, portal refuses), fall back to today's fail-closed path: `detachDependents`, drop the secret, status `needs-credentials` with the sign-in hint.
4. A read that fails with an expired-token error is classified `needs-credentials` (extend `classifyAttachError` and `connections` error codes) and triggers one rotate (rate-limited) so the next statement works if the cache has a fresh token.

The hub gains `session.WithStatusListener(func(name string))` so Studio can emit `connection:status` for changes it did not start itself (a rotation that failed during an agent or MCP statement).

A dropped secret does not stop reads DuckDB serves from its external file cache (#118 spike): that is data already read with valid keys, not an anonymous read, but tests that assert "no read after the secret is gone" must read an object not read before (or turn the cache off).

### D10. #131: status, prompt and headless behaviour

- `secrets.ErrNeedsCredentials` gains a non-secret `SignIn *SignInHint{Kind: "aws-sso", Subject: profile, Reason: "missing"|"expired"}`; `session.Status` carries it (`sign_in` in JSON) on `needs-credentials`. Messages: "AWS session for profile **dev** has expired. Sign in, or run `aws sso login --profile dev`." No account id, role name or start URL in messages (they are not secrets, but they are more than the person needs and they reach the agent's error text).
- `CredentialStatus` for `aws-sso` reports `Method`, `Profile`, `SignedIn`, `ExpiresAt` (of the SSO session, from the cache), never a key.
- **Studio:** a `useSignIn` module singleton (like `useDotEnv`) lists connections whose status has an `aws-sso` hint; a new `SignInBanner.vue` (beside `WorkspaceBanner`) shows "AWS session for profile **dev** has expired: Sign in / Not now". "Not now" is per workspace open (cleared on `workspace:opened`); the banner starts its own tracking in `onMounted`, as `WorkspaceBanner` does. Sign in starts the flow, shows the user code and a Cancel, and on success Preflights the storage connection (which `readyDependents` its lakes), then `refreshConnections()`. The rail's "Sign in" action on such a connection starts the same flow instead of opening `CredentialsPromptDialog`.
- **Headless MCP** (`vibe mcp serve`) and every CLI path other than the explicit sign-in command: status `needs-credentials` with the hint; a query that needs it fails at once with that message. No code path there can start a device flow (the flow lives behind a Studio binding and one CLI command).
- **CLI mirror** of the Sign in button: `vibe conn credentials sign-in <name>` (prints the URL and code, opens nothing, waits up to the code's expiry, Ctrl-C cancels).
- **Open latency.** Preflight runs synchronously at open (grounding), so `awssso` caches per profile for the life of the process: a success until `Expires - 5 min`, and a "couldn't reach AWS sign-in" or "needs sign-in" result for 30 s, so N connections on one profile cost at most one 5 s wait when offline. `vibe conn test` and `conn credentials status` print the hint with both `vibe conn credentials sign-in <name>` and `aws sso login --profile <p>`.

## Security: what the adversarial reviewer should hit

- **Step 1.** Scope suggestion widening: craft URLs whose common prefix collapses to the bare scheme or another bucket (`s3://a/x` + `s3://ab/y`; trailing-dot or empty segments; mixed `s3://` and `s3a://`); `gs://` vs `gcs://` aliasing; an abfss host that is not the account's own endpoint (the suggestion must not propose a scope `azureType.Validate` would refuse); suggestion names that are SQL keywords, reserved, or collide with an existing connection in a different scope; `checkStorageURL` behaviour changed by the refactor (same table test).
- **Step 2.** The binding as an oracle: does it reveal anything `ListConnections` doesn't (another scope's shadowed connection, a credential state, an `env:` variable)? Size/DoS limits; a URL with control characters reaching a log line; the status shown for a match leaking a raw error. Presets: a preset can only fill the three options, `endptRE` still applies, `<region>` left unreplaced is refused, the region input cannot inject a path into the endpoint.
- **Step 3.** Prefill as an injection channel: a crafted in-app link (a notebook's markdown or an A2UI artifact rendering `#/connections/new?type=s3&prefix=s3://attacker/&in=user`; markdown drops non-`http(s)` hrefs today, so check A2UI, the agent transcript and anything else that can navigate) prefilling a connection the person saves without noticing (prefill must be visible, never auto-save, `in` limited to own scopes, and a crafted `type` ignored). The draft stash must not persist to disk or survive a workspace switch (a draft from workspace A restored into B). The leave guard bypass must not drop unsaved storage credentials silently.
- **Step 4.** The throwaway test session now holds a real storage secret: confirm it is hardened like the hub (no community extensions, no autoinstall, private extension dir), closed after the test, and that its `SCOPE` is the saved connection's, not the lake's URL. The lake test must not use a storage connection whose credential guard (fingerprint, `env:` binding) would withhold it in the session. Catalog vetting over httpfs still refuses crafted catalogs. The CLI hint must not print credentials or `${ENV}`-expanded values of the lake definition.
- **Host `AWS_*` (#135, fixed before this step).** httpfs copies the host's `AWS_*` into `s3_*` settings at load; `session.DenyUncoveredStorage` adds catch-all deny secrets so an uncovered URL fails closed, and storage secrets write `SESSION_TOKEN`/`REGION` explicitly. The rotation/SSO secret written in step 6 must keep emitting both fields.
- **S3 URL parameters (#138, fixed before step 6).** httpfs lets `?s3_endpoint=`, `s3_use_ssl`, `s3_url_style` and `s3_access_key_id` in a URL override the matched secret, which would send an SSO session token and a valid signature to a host a manifest or a typed query chose. Every session that loads httpfs sets `s3_url_compatibility_mode` (the URL is the key; S3 globs are off) and reads it back, in `session.DenyUncoveredStorage`. **Any new secret path in steps 6-7 (the SSO secret, the rotation that replaces it in place, a new session or hub option) must load httpfs only through `session.EnsureExtension`/`applyHardening`, never `LOAD httpfs` by hand, and must keep the setting on.** Review: with a fake SSO profile and a loopback fake S3, read `s3://<scope>/x.parquet?s3_endpoint=<other loopback>&s3_use_ssl=false&s3_url_style=path` and a DuckLake relative path with the same suffix, and `require` `current_setting('s3_url_compatibility_mode')` and `which_secret` before reading (see `internal/session/url_params_test.go`); the other host must see nothing. Do not use the secret option `URL_COMPATIBILITY_MODE` (a no-op in 1.5.6).
- **Step 5.** `awssso`: `AWS_*` environment, `AWS_PROFILE`, `AWS_ENDPOINT_URL*`, `AWS_CONFIG_FILE` pointing at a workspace file, IMDS reachability — none may change which identity is used or where tokens are sent (only `sso_region`-derived endpoints; endpoint env vars ignored). Profile files that mix `sso_*` with `credential_process` (must be refused, not partially honoured). Token, refresh token, client secret, role keys in any error or log.

A pulled change to `endpoint`/`scope`/`region`/`use_ssl` withholds SSO credentials until re-confirmed.
