# Packaging and release plan: macOS and Linux

> **How Vibe ships in v0.1.0: unsigned.** A release is a pushed tag. GitHub Actions builds native tarballs for Linux and macOS (amd64 and arm64), ad-hoc signs the macOS app, publishes `checksums.txt`, and attaches [`install.sh`](https://github.com/SandwichLabs/vibe/blob/main/install.sh), which is how people install it ([`install.md`](install.md)). There is no notarisation, no Apple Developer ID, no `.deb`/`.rpm`, no Homebrew tap and no silent auto-update (an opt-in in-app update check that re-runs `install.sh` after you confirm exists; see [`install.md`](install.md#upgrade)). The first sections below ("v0.1.0 unsigned pipeline", "macOS unsigned path", "Installing") describe that path as built. Everything from "1. Where things stand" on is the **signed distribution plan** (epic #4) that comes after v0.1.0; where it disagrees with the unsigned sections, the unsigned sections win.

**Date:** 2026-09-23 (unsigned sections updated 2026-10-12)
**Status:** The unsigned pipeline and installer are built (#46, #47); the macOS spike (#43) is done. The signed plan (§2 onward: notarised dmg, deb/rpm, Homebrew, GoReleaser) is **proposed and not built**. Tracking: epic #4.

Vibe ships two binaries: `vibe` (CLI, TUI, `vibe mcp serve`) and
`vibe-studio` (the Wails desktop app). Both are CGO (DuckDB, and
for Studio, WebKit), which decides almost everything below.

## v0.1.0 unsigned pipeline, as built (#46)

This supersedes the GoReleaser/signing plan in §5.3 and §7 for v0.1.0. `.goreleaser.yaml` and `task release:*` are gone; a release is **push a tag**.

- **Trigger:** `.github/workflows/release.yml` on `push` of `v*` tags, or `workflow_dispatch` with an existing tag. `-rc` and `-test` tags are prereleases. Every release is a **draft**; a human publishes it.
- **Native matrix** (no cross-compiling CGO): linux amd64 `ubuntu-22.04` (glibc 2.35 baseline, never newer), linux arm64 `ubuntu-22.04-arm`, darwin arm64 `macos-15`, darwin amd64 `macos-15-intel` (`macos-13` is retired).
- **Versions:** the tag minus `v` is stamped into the CLI (`cmd.version/commit/date`) and Studio (`main.version/commit/date`), and `wails.json` `info.productVersion` is set for the build only (`scripts/stamp-wails-version.sh <ver> wails build ...` restores the file afterwards, locally too: `task build:studio*` stamps `git describe`). `vibe --version` and `vibe-studio --version` show the tag; the build job fails if they do not.
- **Archives** (built by `scripts/package.sh`), per platform:
  - `vibe_<ver>_<os>_<arch>.tar.gz`: `vibe`, `VERSION`, README, LICENSE, NOTICE and THIRD_PARTY_NOTICES.md (the last three are required: `package.sh` fails without them). `THIRD_PARTY_NOTICES.md` is generated by `task notices` (`scripts/gen-notices.mjs`: go-licenses v2 over the CLI and Studio on linux and macOS, the production npm packages, DuckDB's bundled components, fonts and icons). It fails on a licence outside the permissive allow-list, and CI fails when the committed file is stale; rerun `task notices` after any dependency change. The text is also embedded in Vibe Studio only (`legal.go`, for Settings > About); the CLI carries it only as the file in its archive. `--check` needs network the first time (it runs `go install` of go-licenses v2.0.1, pinned in the script rather than as a go.mod `tool`, which would add its dependency tree to go.mod).
  - `vibe-studio_<ver>_<os>_<arch>.tar.gz`, macOS: `Vibe Studio.app/` (ad-hoc signed), `vibe`, `VERSION`.
  - `vibe-studio_<ver>_linux_<arch>.tar.gz`: `bin/vibe`, `bin/vibe-studio`, `share/applications/vibe-studio.desktop`, `share/mime/packages/vibe-bundle.xml`, `share/icons/hicolor/<N>x<N>/apps/vibe-studio.png` (16 to 512) and `scalable/apps/vibe-studio.svg`, `VERSION`.
- **Icon (#44):** the master is `studio/build/icon/vibe.svg` (SchoolHouse teal tile, cream "V" over a wave). `scripts/gen-icons.sh` (needs ImageMagick) writes `studio/build/appicon.png` (1024², committed; `wails build` makes the macOS `iconfile.icns` from it and `studio/icon.go` embeds it as the Linux window icon) and the Linux hicolor tree under `studio/build/linux/icons/`. The installed icon name is **`vibe-studio`** (`Icon=vibe-studio` in the `.desktop` file); install.sh (#47) and the deb/rpm must install `share/icons/hicolor` from the archive as-is.
- **macOS minimum (#44):** the bundle is `Vibe Studio.app` (package.sh renames Wails' `vibe-studio.app`). `scripts/macos-target.sh` gives 14.0 (arm64) and 13.0 (amd64); release.yml uses it for `MACOSX_DEPLOYMENT_TARGET` and `CGO_CFLAGS`/`CGO_LDFLAGS=-mmacosx-version-min=...` (CLI and Studio), package.sh stamps `LSMinimumSystemVersion` (the committed template says 13.0) before signing, and a release step runs `scripts/check-macos-minos.sh`, which fails if `vtool -show-build` reports a `minos` above the plist value. Not runnable on Linux.
- **Prerelease versions:** a `-rc` tag gives a non-integer `CFBundleVersion` (for example `0.1.0-rc.1`). That is fine unsigned; revisit it with signing and notarisation (#4).
- **`vibe studio --gui` (#44):** looks for `vibe-studio` beside the real `vibe` (symlinks resolved), then on `PATH`, then on macOS for `Vibe Studio.app` beside the CLI, in `~/Applications` and `/Applications`, started with `open -a` (`cmd/studio_gui.go`).
- **Build tags:** `duckdb_arrow` everywhere (Linux adds `webkit2_41`); `wails.json` installs the frontend with `npm ci` (`frontend:dev:install` stays `npm install` for `wails dev`).
- **macOS:** `codesign --force --deep -s -` (no hardened runtime, so downloaded DuckDB extensions still load), then `codesign --verify --deep --strict`. No notarisation.
- **Release job** (the only one with `contents: write`): `checksums.txt` over all archives, `actions/attest-build-provenance` on every archive, `install.sh` uploaded when it exists in the repo root, notes from the matching `CHANGELOG.md` section or auto-generated. Attestations need GitHub Enterprise on a private repo, so the step runs only when `github.event.repository.private == false` and starts working when the repo goes public.
- **Installer (#47):** `install.sh` (repo root, POSIX sh, attached to every release). See "Installing" below.
- **Deviation from audit §4:** asset names carry the version (`vibe_<ver>_<os>_<arch>.tar.gz`, `x86_64`/`amd64` as `amd64`). `install.sh` resolves the latest tag from the `releases/latest` redirect (#47). The archive contents follow §4.
- **Safety:** the tag is validated against `^v[0-9]+\.[0-9]+\.[0-9]+(-[0-9A-Za-z.]+)?$` before use (also for dispatch input), builds use no caches, and a re-run refuses to touch a release that is already published. Any `-suffix` tag is a prerelease. Archives are reproducible (sorted, root-owned, commit-time mtimes).
- **Cutting a release:** `git tag -a v0.1.0 -m "Release v0.1.0" && git push origin v0.1.0`, review the draft, then publish it. `task release` prints this.

### Recommendations

- **`LSMinimumSystemVersion` (#44): `14.0` for arm64, `13.0` for amd64**, stamped per arch in CI (the archives are per arch), not the current `10.13.0`. Say "macOS 14 or later (Apple silicon), 13 or later (Intel)" in the README. Raising arm64 to 14.0 matches the DuckDB static library and removes the warnings; do not claim 13 on arm64 until a macOS 13 or 14 machine has run it.
- **Set the deployment target in `release.yml` for the CLI too** (`MACOSX_DEPLOYMENT_TARGET` plus the cgo flags above, per arch); otherwise the CLI is `minos 15.0`. Add a check that fails the build if `vtool -show-build` reports a `minos` above the plist value.
- **install.sh (#47):** downloading with `curl` and extracting with `tar` is the supported path, because it leaves no quarantine attribute. Never `xattr`, `chmod` inside the bundle, or `cp` files into it after the archive is extracted (the signature seals the bundle). Use `ditto` or `cp -R` to place the app, never a browser. On macOS 15 a browser-downloaded archive needs System Settings, Privacy & Security, **Open Anyway** (or `xattr -dr com.apple.quarantine`); put that on the release page. Check `uname -m` and map `x86_64` to `amd64`. After installing, run `codesign --verify --deep --strict` and `vibe --version`.
- **Do not turn on the hardened runtime** for the unsigned release. It is not needed and is not what breaks extensions here, but it becomes the failure mode as soon as #4 signs with a Developer ID: then add `com.apple.security.cs.disable-library-validation`.
- **Needs a human on a real Mac:** the first-use keychain dialog after an upgrade, TCC prompts, a Finder double-click on a `.vibe`, and macOS 13/14.

## 1a. File opening, as built (#105 Slice 3)

What the app does, whichever way the OS hands it a path. All of it is `studio/workspace_launch.go` (`classifyLaunchArg`, `resolveLaunch`, `handleOpenPath`, `GetInitialWorkspace`, `MarkLaunchHandled`) and `studio/frontend/src/App.vue` (`handleOpenRequest`).

The launch target is used once: `GetInitialWorkspace` only reads it, and the frontend calls `MarkLaunchHandled` after the open is handled (opened, failed or declined), so a later reload shows the Launcher instead of reopening it.

| Path is | Studio does |
|---|---|
| a directory | opens it as a workspace (asks "Make this folder a workspace?" when it has no `vibe.yaml`; asks before leaving an open workspace) |
| a `*.vibe` file (any case) | opens the **Import .vibe…** dialog with the file already chosen: into the open workspace, or as a new one from the launcher. The file is read, verified and previewed first; nothing is written until **Import**. A v1 container or any non-bundle gets the plain "not a Vibe bundle" message from the preview |
| anything else, or a missing path | a plain-language notice (on the launcher, or a dismissible banner when a workspace is open) |
| a flag (`-psn_...`, `--x`) | ignored |

- **Linux and argv.** `vibe-studio <path>` and `vibe studio --gui <path>` (which execs `vibe-studio` with the absolute path; a `.vibe` is passed through to Import, only the terminal UI refuses one). A desktop entry's `Exec=vibe-studio %U` passes `file://` URIs, which are percent-decoded; only the first path is used.
- **macOS and Apple Events.** `mac.Options.OnFileOpen` (Wails v2.11) calls the same handler. Finder launches the app with no path in argv, so a path can arrive **before** the frontend is ready (cold launch by double-click) or **after** (the app is running and a folder is dropped on the Dock icon). Before: the path is queued and the frontend collects it with `GetInitialWorkspace()` on mount (the last one wins). After: the backend emits an `app:open-path` event with the same `{path, bundlePath, message}` shape, and the frontend handles it exactly like the startup case. The first `GetInitialWorkspace()` call is the moment the backend switches from queueing to emitting.
- **Verification.** The classification, the `file://` handling and the queue-then-emit switch are unit-tested (`studio/workspace_test.go`), the frontend routing in `App.spec.ts`. **Not verified on a Mac**: the darwin build needs CGO and a Mac toolchain, so `GOOS=darwin go vet ./studio/...` does not run on Linux, and whether Finder really fires `OnFileOpen` for a folder is one of the spike's questions (§6, step 1). The Wails option is plain Go and compiles on every platform.

### The macOS bundle

`studio/build/darwin/Info.plist` (committed; `studio/build/` is un-ignored except `bin/`) sets `CFBundleIdentifier` `dev.sandwichlabs.vibe-studio` and declares:

- `CFBundleDocumentTypes`, **Viewer** role for both:
  - **folders** (`public.folder`, `LSHandlerRank` Alternate): Vibe appears in *Open With* for a folder and can be chosen, but never becomes the default handler for folders;
  - **Vibe bundle** (`dev.sandwichlabs.vibe-bundle`, rank Owner).
- `UTExportedTypeDeclarations`: `dev.sandwichlabs.vibe-bundle`, conforming to `public.data`, extension `vibe`, MIME `application/x-vibe-bundle`, description "Vibe bundle".

Wails still fills in the product name, version and copyright from `wails.json` (`info`). The description everywhere says "Vibe bundle", not "Vibe database".

### The Linux files

- `studio/build/linux/vibe-studio.desktop`: `Exec=vibe-studio %U`, `MimeType=application/x-vibe-bundle;`, `Icon=vibe-studio`.
- `studio/build/linux/vibe-mime.xml`: `*.vibe` → `application/x-vibe-bundle`, comment "Vibe bundle".
- **Decision: the `.desktop` file does not claim `inode/directory`.** That MIME type would add Vibe to *Open With* for every folder on the machine and, on some desktops, compete for the "open folder" default, which is the file manager's job. A workspace folder is opened with `vibe-studio <dir>` or `vibe studio --gui <dir>`, or from Studio's own launcher (Open folder…, recent workspaces). People who want a file-manager entry can add one themselves (a Nautilus script or a Dolphin service menu that runs `vibe-studio "$@"`); this is documented, not shipped. Revisit if testers ask.
- **Install steps** (for the nfpm package, §5.3, and `install.sh` in the tarball): `/usr/share/applications/vibe-studio.desktop`, `/usr/share/mime/packages/vibe-bundle.xml` (installed under that name), hicolor icons; post-install runs `update-desktop-database` and `update-mime-database /usr/share/mime`. The nfpm config itself is part of the pipeline work in #4.

## Installing (install.sh, #47)

```sh
curl -fsSL https://sandwichlabs.dev/vibe/install.sh | sh                        # CLI + Studio
curl -fsSL https://sandwichlabs.dev/vibe/install.sh | sh -s -- --cli-only       # servers, MCP-only
curl -fsSL https://sandwichlabs.dev/vibe/install.sh | VIBE_VERSION=v0.1.0 sh    # pin a version
curl -fsSL https://sandwichlabs.dev/vibe/install.sh | sh -s -- --uninstall
```

Flags: `--version vX.Y.Z`, `--cli-only`, `--install-dir DIR` (env `VIBE_INSTALL_DIR`), `--force`, `--uninstall`, `--dry-run`, `--help`. Env: `VIBE_VERSION`, `VIBE_APP_DIR` (macOS, default `~/Applications`), `VIBE_DOWNLOAD_BASE` (mirror), `NO_COLOR`. It never uses `sudo`, sends no telemetry, and the whole script is one brace group, so a truncated download runs nothing.

- **Resolve and verify.** `latest` is read from the `releases/latest` redirect (no API; needs curl). It downloads the archive and `checksums.txt` (curl, or wget for pinned versions), matches the archive's exact name in `checksums.txt`, and aborts on a mismatch or a missing entry before touching anything. Archives with `..`/absolute paths, links or special files are refused.
- **Where files go.** The CLI to `~/.local/bin`. Linux Studio: `vibe-studio` beside it, the `.desktop` file (absolute, quoted `Exec=`) in `~/.local/share/applications`, the MIME XML in `~/.local/share/mime/packages`, the hicolor icons from the archive in `~/.local/share/icons/hicolor`, then `update-mime-database`, `update-desktop-database` and `gtk-update-icon-cache` when present (the cache file it writes is left in place on uninstall). macOS Studio: `Vibe Studio.app` in `~/Applications` via `ditto` (no quarantine bit with curl; nothing in the bundle is touched afterwards), checked with `codesign --verify --deep --strict`. No `vibe-studio` wrapper is installed on macOS: `vibe studio --gui` finds the app itself (`open -a`, see #44).
- **Collision guard.** `~/.local/bin/vibe` is replaced only when its sha256 matches the manifest, or (first install over an older copy) the file contains Vibe's Go module path. Anything else (Mistral Vibe uses the same name) stops the install and points to `--force` or `--install-dir`. Foreign programs are never executed to find out. A different `vibe` earlier on `PATH` only warns.
- **Checks that warn, not fail.** Missing WebKitGTK/GTK (via `ldd`, with an apt/dnf/pacman/zypper line) and no Secret Service on the session bus. The CLI works without both. musl and glibc older than 2.35 are refused; macOS older than 14 (arm64) or 13 (Intel) is refused unless `--force`.
- **Manifest, upgrade, uninstall.** `~/.local/share/vibe/install-manifest` (macOS: `~/Library/Application Support/vibe/`) records `version=` and, per file, `F <sha256> <path>` (the macOS app is `D - <path>`). Re-running is the upgrade: files are replaced, files the new version no longer ships are removed, `0.1.0 -> 0.2.0` is printed. `--uninstall` removes only entries of the shapes the installer writes (`vibe`, `vibe-studio`, its `.desktop`, MIME and icon files, the `Vibe Studio.app` directory) whose hash is unchanged, says which it kept, and lists what it never touches: config, the extension cache, keychain items and workspaces.
- **Tests.** `scripts/test-install.sh` builds fake releases with the real `scripts/package.sh`, serves them from a local HTTP server and runs the scenarios (install, `--cli-only`, collision, upgrade, uninstall, `latest`, dry run, unsupported arch, missing libraries, and hostile releases: swapped, undeclared or decoy checksums, traversal and symlink archives, tampered manifest, replaced binary) in unprivileged ubuntu:22.04, ubuntu:24.04, debian:12 and fedora:latest containers. `--native` runs it on the host. `--assets DIR --tag vX.Y.Z` smoke-tests real release assets; `.github/workflows/install-test.yml` does that after a release is published (or manually, for a published tag), on those images plus macos-15 and macos-15-intel.
- **Testing a release candidate.** `install-test.yml` holds only `contents: read`, so rc1 must be published as a prerelease first; or test locally with `gh release download <tag> --dir dist` (needs write access for a draft) and `scripts/test-install.sh --assets dist --tag <tag>`.
- **Hosting.** `https://sandwichlabs.dev/vibe/install.sh` redirects to `https://github.com/SandwichLabs/vibe/releases/latest/download/install.sh` (outside this repo). User-facing install steps are in [`install.md`](install.md).

Linux baseline: built on **Ubuntu 22.04** (glibc 2.35), against
**webkit2gtk-4.1**. That covers Ubuntu 22.04+, Debian 12+, and Fedora 36+.
RHEL 8 / Debian 11 have no webkit2gtk-4.1 and are out.

Deferred, not rejected:
- **Flatpak.** The GNOME runtime ships WebKitGTK 4.1, so this is the best path
  to "any distro". Flathub review adds lead time.
- **AppImage.** Bundling WebKitGTK's helper processes is fragile and large.
- **Snap.**
- **Sparkle and package-manager updates.** The in-app update check plus `install.sh`-driven apply is built (`internal/selfupdate`, `vibe update`, Settings > About > Updates). Sparkle on macOS is still deferred; Linux package installs update through the package manager.
- **Windows.** The DuckDB bindings support it; there is no signing story yet.

## 3. Toolchain choice

GoReleaser OSS can't do most of the macOS half. Checked against goreleaser.com
2026-09: `app_bundles`, `dmg`, `pkg`, native sign+notarize, versioned casks,
the `prebuilt` builder, and split/merge builds are **Pro-only**. OSS
notarization uses quill, which is binary-only. The docs warn that an `.app`
where only the binary is signed "is deemed damaged by macOS."

Studio also needs a real Mac (`wails build`, WebKit/Cocoa frameworks,
`codesign`, `notarytool`) and a native Linux per arch (WebKitGTK dev headers).
So:

**Recommended: GoReleaser OSS for the Linux CLI and the release itself;
a native-runner matrix for Studio.**

- **GoReleaser OSS** (one `ubuntu-22.04` job):
  - changelog
  - Linux CLI builds (amd64 native, arm64 via `aarch64-linux-gnu-g++`)
  - CLI tarballs, `checksums.txt`, and the Homebrew formula
  - creates the GitHub release **as a draft**
- **Studio matrix** (`macos-15`, `ubuntu-22.04`, `ubuntu-22.04-arm`):
  - `wails build`, plus a native `go build` of `vibe` on the same runner
  - packaging: `.app` → dmg on the Mac, nfpm on Linux
  - uploads to the draft with `gh release upload`
- **Publish job**: re-checksums every asset, pushes the cask to the tap,
  flips the release from draft to published.

Alternatives considered:

| Option | Pros | Cons |
|---|---|---|
| **A. Recommended** (above) | $0 beyond the Apple account. Every build is native, so no osxcross. GoReleaser still owns changelog, formula, and release. | Two packaging systems: GoReleaser, and the scripts in `packaging/`. The cask is templated by hand. |
| **B. GoReleaser Pro** | One config: split builds per runner, merge, `app_bundles`, `dmg`, native notarize, versioned cask, nfpm, all in `.goreleaser.yaml`. | Paid licence. Still needs the same three runners. Wails' own bundle step would be replaced by GoReleaser's. |
| **C. goreleaser-cross** (osxcross Docker image, one Linux job builds everything) | One job for the CLI. | Can't build Studio (WebKit on Linux-for-mac is not realistic). Cross-linking DuckDB's static lib through osxcross is a risk. The Mac notarization problem remains. |

Pick B only if the two-system split in A gets annoying. The workflow shape is
the same, so switching later is cheap.

## 8. Decisions and checks that stay open in #4

### DuckDB extensions: pinning and bundling

- **Pinned engine.** duckdb-go (`github.com/duckdb/duckdb-go/v2`) is pinned to a DuckDB version MotherDuck supports (v2.10506.0 = DuckDB 1.5.6 today; it moved from `marcboeker/go-duckdb` in #118). Bumping it is a deliberate change, checked against MotherDuck, never a routine `go get -u`. Extension binaries are per DuckDB version and platform, so a bump also changes what has to be downloaded or bundled.
- **Download on consent, into the app-private directory.** Autoinstall and autoload are off; `extension_directory` is `<user cache dir>/vibe/duckdb/extensions`; a missing extension is a visible `extension-missing` state and the download happens only on the person's yes (Studio's Install, or `--install` on the CLI). The user's own `~/.duckdb` is never loaded. Details: [reference/connections.md](reference/connections.md#duckdb-version-and-extensions). `vibe workspace info` shows the running version and what is installed.
- **Open decision: bundle an offline set?** Options:
  - bundle nothing (today): smallest download, needs network the first time each extension is used;
  - bundle `excel` only (the one a non-technical person meets first, for xlsx import and export);
  - bundle the full set (`excel`, `httpfs`, `postgres`, `mysql`, `sqlite`, `azure`, `ducklake`, `iceberg`, `delta`, `motherduck`): works air-gapped, adds tens of MB per platform and a per-version rebuild, and every bundled dylib must be signed (macOS) or packaged with its checksum.
  Whichever is chosen, point `extension_directory` at a read-only bundled directory first and the user cache second, and keep the consent step for anything not bundled. Decide in the spike, with the hardened-runtime result in hand.

### Keychain access from signed builds

go-keyring talks to the macOS Keychain by running `/usr/bin/security`, and to the Secret Service over D-Bus on Linux. Both are exercised in development, but not from a signed, notarised, hardened-runtime `Vibe Studio.app`. Checklist item for #4, before the first public Mac build:

- [ ] On a signed and notarised build: save a connection credential in Studio, quit, relaunch, and read it back (Test the connection). Confirm no unexpected keychain prompt appears on every launch, and that the item is visible to a **re-signed** build of the next version (the keychain item's access list can be tied to the signing identity; if each release re-prompts, the secrets store needs an explicit access policy or the Data Protection keychain).
- [ ] Same for the LLM API key, and for `vibe` (the CLI inside the bundle) reading a credential Studio saved, since both must see one item.
- [ ] On Linux: a headless box with no Secret Service. Confirm the "no keychain" message is clear and that `env:` references (the CI path) still work.

If the check fails, the fallback is **not** a plaintext file (see the direction doc's non-goals); it is `env:` references plus a clear message.
